A toolbox for you and your agents

Bring data, APIs, and workflows together so you and your AI tools can spend less time on plumbing.

An agent can help you reason through a problem, but reasoning is only part of the work. To make progress it also needs useful, appropriate tools: somewhere to store information, a way to query it, and operations that can carry out the next step.

mAIcro is a toolbox for that work. It isn’t primarily about building agents; it’s about giving you and the agents you choose a place to work with data, documents, APIs, and processes.

Show them, don’t just tell them

A description can start a conversation, but a working prototype gives people something concrete to explore. Show how a solution behaves, invite questions, and use the feedback to decide what to improve. It doesn’t need to be finished to make an idea easier to understand.

Start with the data

mAIcro uses PostgreSQL and exposes a GraphQL API. Define a table and reload the schema to get generated types, queries, and mutations. That gives a prototype a usable data layer without writing a separate CRUD API for every table.

The same environment supports vector embeddings and similarity search, as well as graph queries through Apache AGE and openCypher. Choose the model that suits the question: structured fields for records, vectors for similarity, and graphs for relationships. They are tools to combine where they help, not requirements for every project.

Give the work somewhere to go

Use chains to compose operations into workflows. Wrap a parameterized SQL query or an external REST API as a named GraphQL operation when you need to bring another capability into the project. TypeScript modules provide another way to extend the platform.

With MCP enabled, compatible AI clients can access mAIcro’s tools, including GraphQL operations and schema information. The agent remains your chosen client; mAIcro supplies capabilities it can use. Check the client’s configuration and permissions before connecting it, particularly for operations that change data.

Try a small, inspectable loop

Imagine you want to show a team how requests could be triaged. Begin with a handful of fictional requests, each with a title, description, and status. Your first goal is modest: add a request, list the open ones, and update a status.

  1. Define a table for the example and call DbReload after the schema change.
  2. Use the generated GraphQL operations in the IDE to add and query a few records.
  3. Add a workflow only when there is a step worth repeating. For example, an AI task could suggest a category for a request.
  4. Inspect the suggestion alongside the original request. Keep the decision with a person and test an input that does not fit the expected categories.

Now you have something to demonstrate: a small data model, an observable operation, and a result people can question. Their feedback can tell you whether the idea is useful before you invest in a complete application.

Keep control of the boundaries

An agent with access to a tool may be able to change data, not just read it. Use a disposable project and sample data while experimenting; check which operations and credentials the client can use. Review mutations and external requests before running them.

Run mAIcro locally in Docker or self-host it. Local hosting doesn’t mean every connected service is local: external AI providers and APIs receive the information you send them. Check provider terms, network exposure, and data-sharing choices before using sensitive information. A prototype is a learning tool, not proof that an application is ready for production.

For a practical integration to explore, start with the API Wrappers course. Its public example uses a fake REST API; review the setup and its effects before running any scripts. You can also get mAIcro running and start with your own small problem.
